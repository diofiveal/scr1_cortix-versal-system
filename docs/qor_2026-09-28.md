# Timing and power follow-up (Vivado 2023.2, VD100)

The original routed reports (`timing.rpt`, `power.rpt`, 2026-09-28) show:

| Measurement | Original | Interpretation |
| --- | ---: | --- |
| PL clock | 100 MHz / 10 ns | The SCR1 target is constrained. |
| Setup WNS / TNS | -0.367 ns / -196.870 ns | 941 failing endpoints; hold WNS is +0.026 ns. |
| Worst data path | 10.273 ns | 27 logic levels, 5.317 ns logic + 4.956 ns routing. |
| Power estimate | 5.226 W | 2.857 W dynamic + 2.370 W static; **Low** confidence. |
| Junction estimate | 100.0 °C | Based on 25 °C ambient and 14.4 °C/W effective TJA. Not a measured board temperature. |

The worst setup path starts in the SCR1 trigger-debug unit (TDU), traverses the
one-cycle 32-bit multiplier in two cascaded DSP58s, and ends at the SCR1 register
file. The MAX architecture preset enables `SCR1_FAST_MUL`. This project now
selects SCR1's existing iterative multiply implementation, **without disabling
the RISC-V M extension**. This is a timing/throughput tradeoff: all multiply
instructions take multiple cycles. Division was already iterative. Removing
`SCR1_VD100_ITERATIVE_MUL` from `rtl/config/scr1_arch_custom.svh` restores the
previous behavior. The new path and all 941 failing endpoints must be measured
after a fresh synthesis and route; the original reports contain only one setup
path detail and do not establish that every failing path uses the multiplier.

## Rebuild and measure

In the existing Vivado project, reset and rerun `synth_1`, then reset and rerun
`impl_1` after pulling these RTL changes. Do not reuse the old routed DCP for
the new multiplier configuration. In Vivado Tcl console, for example:

```tcl
reset_run synth_1
launch_runs synth_1 -jobs 4
wait_on_run synth_1
reset_run impl_1
set_property strategy Performance_ExplorePostRoutePhysOpt [get_runs impl_1]
launch_runs impl_1 -jobs 4
wait_on_run impl_1
```

The implementation strategy is an additional experiment, not a timing
exception. It enables post-route physical optimization; compare it against a
default implementation with the **same RTL** if the timing margin matters.
Never apply a false path or relax the 100 MHz clock to conceal this failure.

From the repository root, after routing:

```sh
vivado -mode batch -source scripts/scripts/vivado/analyze_routed.tcl \
  -tclargs /absolute/path/to/vd100_scr1.xpr
```

Reports are written beside the XPR under `qor_reports/`. Check WNS >= 0,
TNS = 0, setup/hold endpoint counts, and the top 50 detailed paths. Confirm
that the cascaded DSP multiplier has left the worst path; the next bottleneck
may require a separate RTL change. Also run instruction-level tests for all
`MUL`, `MULH`, `MULHSU`, `MULHU` and divide variants, including signed corner
cases, then recheck boot and AXI behavior after synthesis.

## Power diagnosis

The reported 2.857 W dynamic power is dominated by platform logic: `u_platform`
accounts for 2.781 W, while `u_subsystem` is 0.073 W (SCR1 top 0.068 W).
The resource summary separately attributes 1.168 W to I/O, 0.704 W to PS9,
0.520 W to NoC-DDRMC and 0.230 W to XPLLs. Those categories and the hierarchy
are **different breakdowns**; do not add them together. Static device power is
2.370 W and cannot be eliminated by changing the multiplier.

This estimate is not yet suitable for judging board power or thermal safety:
over 75% of I/O inputs have no user activity, fewer than 25% of internal nodes
have user activity, no simulation activity file was supplied, device models
are preliminary, and no design power budget is set. Generate representative
SAIF activity including realistic idle and active intervals, then rerun:

```sh
vivado -mode batch -source scripts/scripts/vivado/analyze_routed.tcl \
  -tclargs /absolute/path/to/vd100_scr1.xpr /absolute/path/to/activity.saif
```

Inspect the `Design Nets Matched` and `Confidence Level` fields of
`power_saif.rpt` before trusting its number. Provide measured board ambient,
cooling/TJA and rail-current limits or a board power budget before claiming a
thermal or electrical pass. The `AVAL-344` RAM activity warning should also be
investigated with a representative RAM workload; do not suppress it by guessing
`USER_RAM_AVERAGE_ACTIVITY`. The three `SYNTH-10` wide-multiplier warnings
should be rechecked after resynthesis.
